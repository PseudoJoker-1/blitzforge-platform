# Lua Damage Log — «Журнал урона»

Что по вам попало, на сколько и что это сделало с вашим HP. То, что игрок обычно
восстанавливает по памяти уже после боя.

В бою мод показывает список последних восьми попаданий, самое свежее сверху, и
суммарный счёт за бой. В ангаре — накопленные итоги, которые переживают
перезапуск клиента.

Каждая строка в бою выглядит так:

```text
#4  ·  -312 HP  ·  HP 1350 → 1038  ·  причина: код 0  ·  источник: не указан
```

## Главное правило: показано только то, что пришло

Мод не выводит ни одного числа, которого он не наблюдал. Ноль вместо
отсутствующего значения не подставляется никогда — ноль, выданный за факт, от
факта неотличим.

Событие `wotbmod.gameplay.damage_received` несёт ровно пять полей
(`WotbModV3DamageEventData`, `events_v1.h:147`): `damage`, `previous_health`,
`health`, `reason_code`, `source_entity_id`. Шестого поля нет. Отсюда таблица
того, что вы увидите, когда поля нет:

| Ситуация | Что в строке |
| --- | --- |
| `damage` / HP отсутствуют в payload | `урон: —`, `HP — → —` |
| `reason_code` отсутствует | `причина: нет в payload` |
| `reason_code` пришёл не целым числом | `причина: значение нечитаемо` |
| `source_entity_id` отсутствует | `источник: нет в payload` |
| `source_entity_id` равен нулю | `источник: не указан` |
| источник есть, сущность видима и названа | `источник: Имя (#4242)` |
| источник есть, сущность видима, имени нет | `источник: #4243, имя не публикуется` |
| источник есть, сущности нет в публичном снимке | `источник: #5555, нет в публичном снимке` |
| источник есть, `entity_public` не опубликован | `источник: #6161, entity_public недоступен` |
| payload не типизирован целиком | `событие получено, payload не типизирован` |
| максимальный HP не получен | `макс. HP: нет данных (причина)`, доля не показывается |
| подписка на урон отклонена | нижняя строка панели говорит об этом прямо |

Последнее — не мелочь. Пустой журнал при отклонённой подписке выглядел бы точно
так же, как тихий бой. Поэтому отказ подписки написан на панели, а не только в
логе.

Событие с непонятным payload **не выбрасывается**: строка появляется всё равно и
честно сообщает, что расшифровать её не удалось. Счётчик попаданий за бой
считает такие события, а сумма урона — нет, поэтому в заголовке отдельно
появляется `без значения урона: N`.

## Про имя атакующего

Надёжного имени атакующего в этом API нет ни для одного случая. Есть только
числовой `source_entity_id`. Мод один раз — на ближайшем кадре после события —
ищет этот id в публичном снимке `wotb.players` (то есть в
`entity_public.enumerate_visible`) и подписывает результат ровно тем, что нашёл.
Повторных попыток нет: сущность, которой нет в снимке сейчас, скорее всего уже
не появится, а опрос каждый кадр — это ровно та работа в кадре, из-за которой
однажды просела частота кадров у игроков.

`enumerate_visible` перечисляет только те машины, которые клиент уже показывает
игроку. Невидимый противник в снимок не попадает и именем не станет. Никакого
скрытого состояния противника мод не читает и прочитать не может.

**Что важно знать про текущий клиент.** В сборке 11.19.0.834 единственный
источник события урона — `Vehicle::set_health` в `loader/wotb_mod_loader.cpp`, и
он заполняет только `damage`, `previous_health` и `health`. Поля `reason_code` и
`source_entity_id` остаются нулевыми, потому что их никто не выставляет. Поэтому
на живом клиенте сейчас каждая строка честно сообщает `причина: код 0` и
`источник: не указан`, а в ангарной сводке видно `без источника в событии: N из N
попаданий`. Это не ошибка мода и не заглушка: это то, что клиент реально
рассказал. Как только bridge начнёт заполнять эти поля, тот же самый Lua-код
начнёт показывать имена — менять в моде нечего.

Словаря значений `reason_code` в API тоже нет: ни в одном заголовке `wotbmod/*.h`
нет перечисления причин урона. Поэтому код печатается числом и никогда — словом.
Слово здесь было бы придумано.

## Про `damage_dealt`

Урона, который нанесли **вы**, в этом моде нет, и это не упущение.
`damage_dealt` в API не существует и не может быть синтезирован: у health-ingress
нет доказанного источника атакующего, поэтому приписать чужую потерю HP
локальному игроку можно было бы только угадав. Runtime по этой же причине не
публикует `wotbmod.gameplay.damage_dealt`, а `wotb.battle` держит для этого поля
отдельную строку-причину. Мод не изобретает то, чего в API нет.

## Про максимальный HP

Максимального HP в событии урона нет вообще: `WotbModV3DamageEventData` его не
несёт. Он берётся из **другого источника** —
`wotb.players.local_player().max_health`, то есть из
`entity_public.enumerate_visible`, — и обращаются с ним как с другим:

- источник подписан прямо в строке: `макс. HP: 1350 (entity_public)`;
- доля оставшегося HP (`осталось 48% от макс.`) считается только когда это число
  получено. Пока его нет, строка говорит `макс. HP: нет данных` и **никакой доли
  не показывает** — доля от выдуманного максимума была бы выдуманной долей;
- опрос ограничен: двенадцать попыток раз в 60 кадров и ни одной после успеха.
  Клиент, который не отвечает, стоит двенадцать вызовов за бой, а не один в
  секунду навсегда.

## Итоги между запусками

Сводка в ангаре хранится через `wotb.config` с backend `storage` (один
JSON-документ под ключом `totals`). Показываются: число боёв, попаданий,
суммарный полученный урон, худшее попадание, сколько попаданий пришло без
источника и результат последнего боя.

Значения по умолчанию не затирают сохранённые. Это устроено структурно, а не
аккуратностью:

- `config.new` не пишет ничего и никогда;
- `get` не пишет ничего: отсутствующее значение отвечается из default и
  помечается как `default`, но обратно не записывается;
- запись выполняется как read-modify-write: документ сначала перечитывается,
  потом на прочитанное накладываются только явно поставленные ключи. Чужой ключ
  в том же документе остаётся нетронутым;
- **неудачное чтение прерывает запись целиком.** Итог, посчитанный поверх
  неудавшегося чтения, — это меньшее число, записанное поверх большего. Поэтому
  при отказе хранилища мод не пишет ничего и говорит об этом в нижней строке.

Если хранилище не читается, все строки сводки показывают `нет данных`, а не нули.
Если в хранилище ещё ничего нет, нижняя строка так и говорит: «Сохранённых итогов
ещё нет» — чтобы нули по умолчанию нельзя было принять за наблюдения.

Итоги записываются один раз за бой, на `battle.ended` или `battle.left`.
Единственный вызов, который что-то пишет, — это `save()`, поэтому неудавшийся
коммит не оставил после себя ничего и второе событие жизненного цикла спокойно
пробует ещё раз; удавшийся не повторяется никогда. Бой, прерванный выключением
мода, в итоги не попадает.

## Управление

Кнопка `ПАУЗА` замораживает список: строки перестают двигаться, и их можно
прочитать. События при этом продолжают записываться в отдельную очередь и
появляются в правильном порядке при нажатии `ПРОДОЛЖИТЬ`. Счётчики в заголовке и
строка текущего HP остаются живыми — заморожен именно список, и заголовок это
показывает словом `ПАУЗА`.

## Видимость

Боевая панель существует только в `BATTLE`, `TRAINING` и `REPLAY` и полностью
размонтируется при `MOD_SCREEN` и `TEXT_INPUT`, поэтому каталог модов она не
перекрывает. Ангарная сводка существует только в `HANGAR` и блокируется в
`MOD_SCREEN`, `TEXT_INPUT` и `RESULTS`. Обе построены на `wotb.panel`, поэтому
монтированием, перепривязкой к активному экрану и освобождением handle-ов
занимается сам модуль.

## Цена в кадре

На кадре, где ничего не произошло, `on_frame` выполняет одну проверку типа, два
вызова `panel:update` (каждый — одно взятие остатка и два чтения поля) и две
проверки булевых флагов. Ни одной аллокации, ни одной строки, ни одного вызова
интерфейса. Проверено на мок-хосте: 186 подряд идущих кадров без событий стоили
ровно ноль вызовов.

- строки перерисовываются только когда что-то изменилось: пришло событие,
  разрешилось имя источника, нажата пауза, панель пересоздана. Максимум 11
  вызовов `set_row`, каждый из которых сначала сравнивает и только при отличии
  идёт через ABI;
- `entity_public.enumerate_visible` вызывается только пока есть неразрешённый
  источник, и раз в 60 кадров пока не получен максимальный HP. После того как оба
  вопроса закрыты — ноль вызовов до конца боя;
- `wotb.timer` намеренно не используется, поэтому собственной подписки на
  `wotbmod.frame.update` у мода нет;
- хранилище читается при обновлении ангарной сводки и пишется один раз за бой.
  Никакого дискового I/O в кадре.

Callback-и событий только дописывают запись в Lua-таблицу. Ни один control не
создаётся и не меняется внутри native event dispatch.

## Права и почему именно они

| Permission | Зачем |
| --- | --- |
| `core` | `wotb.log`, `wotb.context.current` (через `core.get_context`) и `wotb.handles.release`, которым панель отпускает handle активного экрана |
| `events.public` | подписка на `damage_received`, `battle.entered`, `battle.ended`, `battle.left` — четыре topic-а и ни одного лишнего |
| `storage` | один JSON-документ с итогами через `wotb.config` |
| `entity.public.visible` + `game.entity.public` | `entity_public.enumerate_visible`: имя источника и максимальный HP. Оба имени обязательны — слот проверяет полный набор |
| `ui.create`, `ui.modify.own`, `ui.modify.game`, `battle.ui` | таблица `wotb.ui` зарегистрирована через `SetFuncsGuardedAll` и требует все четыре имени сразу; без любого из них ни один вызов панели не пройдёт |

Ничего сверх этого мод не просит. Скрытых данных противника не читает,
автоматизацией игры не занимается, урон, нанесённый игроком, не выдумывает.

## Установка

Скопируйте каталог как:

```text
mods\lua\example.lua_damage_log
```

Имя папки обязано совпадать с `id` из `manifest.json` без учёта регистра.
Убедитесь, что в `mods\mods.ini` включён `wotbmod.lua_host`; отдельная строка для
этого мода не нужна — host сам находит каталоги внутри `mods\lua`.
