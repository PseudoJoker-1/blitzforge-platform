# Ре-анкоринг фиксированных RVA

Биндинг-пак загрузчика зависит от **67 фиксированных RVA** плюс 29 смещений
полей структур. Все они действительны ровно для одной сборки клиента. После патча Blitz SHA-256 не
совпадает, native-биндинги честно выключаются fail-closed — и их нужно
привязать заново.

Раньше это была ручная работа в IDA. Этот инструмент делает её автоматически и
**не требует ни IDA, ни каких-либо зависимостей** — только Python 3.11+.

## Как это работает

Для каждого якоря генерируется *рецепт* — описание того, **как найти** функцию,
а не её адрес:

| Тип | Для чего | Как |
|---|---|---|
| `code_signature` | функции (51 шт.) | маскированная байтовая сигнатура от начала функции |
| `data_xref` | глобалы и vtable (16 шт.) | уникальная инструкция, которая загружает адрес, + смещение операнда внутри неё |

Маскирование — это то, что позволяет сигнатуре пережить пересборку. Wildcard'ом
закрывается всё, что содержит адрес:

- dword, попадающий в диапазон VA самого образа (строка, vtable, глобал) —
  такие значения меняются при каждой пересборке;
- операнд rel32 у `call` / `jmp` / `jcc` — он сдвигается, как только между
  вызывающим и вызываемым что-то поменялось в размере.

Остаются опкоды, кодирование регистров и мелкие immediate — то, что компилятор
воспроизводит, пока не менялся исходник.

Окно растёт по расписанию `16 → 384` байт и останавливается на первом размере,
дающем **единственное** совпадение по всему `.text`. Чем короче окно, тем
устойчивее сигнатура.

## Использование

```bash
# 1. Один раз на известной хорошей сборке — сгенерировать рецепты
python reanchor/cli.py generate "C:\...\wotblitz.exe"

# 2. Доказать, что рецепты находят ровно те же адреса (обязательно!)
python reanchor/cli.py verify "C:\...\wotblitz.exe"

# 3. После патча игры — привязаться к новой сборке
python reanchor/cli.py resolve "C:\...\wotblitz.exe" -o new_pack.json
```

`verify` — не формальность. Рецепт, который не воспроизводит собственный адрес,
хуже отсутствия рецепта: после патча он молча наведёт хук на чужую функцию.
Поэтому тест требует **точного совпадения по всем якорям**, а не по большинству.

Тот же контроль встроен в набор тестов: `python test_reanchor.py`.

## Что инструмент НЕ делает

- **Не пишет в исходники загрузчика.** На выходе — отчёт и таблица-кандидат.
  Продвижение её в биндинг-пак остаётся ручным ревью: неверный адрес — это краш
  в чужой игре.
- **Не восстанавливает смещения полей структур.** 29 констант вида
  `kVehicleHealthOffset` сканированием не находятся; после патча их нужно
  подтверждать вручную. Инструмент их отслеживает и выводит в отчёт, чтобы про
  них нельзя было забыть.
- **Не угадывает.** Если сигнатура не найдена или неоднозначна, якорь помечается
  `UNRESOLVED` с причиной. Ни один адрес не подставляется «по похожести».

## Кворум

Несколько якорей — это boilerplate CRT (`operator new` и подобные), чья
сигнатура совпадает в **любом** бинаре, собранном тем же тулчейном. Поэтому
судить о ре-анкоринге по отдельным попаданиям нельзя: если натравить
инструмент на посторонний exe, один-два якоря всё равно «найдутся».

Значим только агрегат:

| Доля найденных | Поведение |
|---|---|
| < 50 % | `REJECTED`, таблица **не пишется** вообще |
| 50–90 % | пишется с `"trustworthy": false` и предупреждением — только как отправная точка для ручной работы |
| ≥ 90 % | пишется как кандидат (всё равно требует ревью) |

Проверено: на `wotblitz-browser.exe` (посторонний 32-битный exe) резолвится
1/67 = 1 % → `REJECTED`, файл не создан.

## Текущее состояние и честное ограничение

На сборке `11.20.0.887` (`4813544d…`) — **97/97 якорей резолвятся точно** (рецепты перегенерированы 2026-09-03; на 11.19.0.834 было 67/67).

Распределение размеров окна (меньше = устойчивее):

| Окно | Якорей |
|---:|---:|
| 16 б | 13 |
| 32 б | 13 |
| 48 б | 20 |
| 64 б | 13 |
| 96 б | 6 |
| 224 б | 2 |

Два «длинных» — `DefaultSceneLoadFromFile` и `BwEntityDtor`. У последнего рядом
почти идентичный соседний деструктор (`0x0231B820`), тела расходятся только
после ~200 байт. Это самые хрупкие места, при следующем патче смотреть на них в
первую очередь.

⚠️ **Кросс-билд устойчивость измерена один раз (11.19.0.834 → 11.20.0.887, мажорная пересборка):
выжил только 31 из 67 рецептов (46 %), результат честно `REJECTED`.** Два из
31 «найденных» были ложными: `ClientInitialize` (сигнатура указала на чужую
функцию `0x017F9B70`; слот 5 vtable `AvatarControllerBase` и строки функции
дали `0x0118FB90`) и `EngineUpdateAndDrawWindows` (сигнатура дала `0x00C7CF60`,
где IDA не видит функции; единственный вызов из Win32-цикла даёт `0x006E06B0`).
Вывод: после мажорного патча сигнатуры — только отправная точка. Реальную
привязку дали методы, не зависящие от байтов функции: RTTI-vtable (13 vtable и
все виртуальные методы по слоту), запись vtable в конструкторах/деструкторах,
строковые литералы, порядковое выравнивание списков `call` у уже найденных
вызывающих, поиск по маскированному префиксу с проверкой сходства
последовательности инструกций. Скрипты и отчёт: `analysis/pivot_tools_20260903/`.
